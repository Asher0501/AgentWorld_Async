Unified Spatial Object + Constraint System

观察 + 行动。无协议。物理即账本。半径即权限。
Observe + Act. No protocol. Physics is the ledger. Radius is permission.

SpatialObject Constraint SpatialProxy Observe+Act No New Channel

1. Design Principles 设计原则

物品是被动的

SpatialObject 只知自己的空间状态。没有 owner、没有 transfer。被 NPC 调用 move(from, to, qty, r)。

NPC 是主动的

NPC 决定移动什么。参数全是自然语言（take_out / take / put_away）。引擎 dispatch 到 SpaceObject.move()。

约束是物理定律

约束校验物理可行性。不判断"交易是否公平"。独立注册、独立触发。

归属 = LLM 推断

引擎只报位置。LLM 从 sensory 看"金币在 Geralt 手里"——自己推断归属。

Observation + Action

拿出东西 → 对方看到 → 自己判断。无协议，无 pending，无两阶段。

同一条感官管线

SpatialProxy 和苹果箱走完全相同的 sensory pipeline。不建新通道。

2. SpatialObject — 空间物体 物品只知坐标，不知归属

2.1 基类接口

class SpatialObject(ABC):
    # 所有空间物体的统一接口。GoldCoin、IronSword、AppleCrate 全部实现
    # 引擎只知此接口——不知道"这个是金币还是剑"

    @abstractmethod
    def move(self, from_pos, to_pos, qty, new_radius):
        pass
为什么要有: 所有物体统一的"移动"操作。Class Singleton 改注册表字典条目——Entity 改自身 pos 属性。参数全是纯坐标 (x,y)——物品不知道谁在移动自己。
谁调: NPC 执行 take_out / take / put_away / give 时，引擎 dispatch 到这里。
什么时候调: 约束全部通过后——PRE 组校验了"来源位置有足够数量"——才执行 move。 
    @abstractmethod
    def qty_at(self, pos) → int:
        pass
为什么要有: 约束校验的核心——"这个位置有足够的数量吗"。Class Singleton 查 _registry[pos].qty；Entity 返回 1 或 0。
谁调: `qty_non_negative.validate()`——在 agent 执行 move 前查询。
什么时候调: PRE 阶段——在执行任何物理变更之前。 
    @abstractmethod
    def radius_at(self, pos) → int:
        pass
为什么要有: 可见半径决定谁能看见这个物体。r=0 不可见，r=1 手中可见，r≥5 远处可见。
谁调: Sensory 系统——all_near() 内部遍历所有注册条目，用 radius 判断是否渲染。
什么时候调: SensorySystem.update()——每个 tick、每个 observer。 
    @abstractmethod
    def all_near(self, center_pos, view_radius) → list[dict]:
        pass
为什么要有: 感官系统查询"observer 附近有什么物体"。返回所有在半径内的堆叠——跳过 r=0 且不在 observer 自身位置的条目。
谁调: SensorySystem.update()——遍历 entity 后追加遍历 SpatialObject registries。
什么时候调: Phase 1 SENSE——每个 agent 每 tick 一次。

2.2 Class Singleton 实现 — GoldCoin

class ClassSingleton(SpatialObject):
    # 一个类一张空间注册表。所有可互换物共享此实现。
    # 引擎不区分 GoldCoin 和 Apple——都是 ClassSingleton 实例。

    _registry: dict[tuple, dict] = {}     # {(x,y): {"qty":50, "radius":0}}

    def move(self, from_pos, to_pos, qty, new_radius):
        if from_pos not in self._registry:
            return False
        if self._registry[from_pos]["qty"] < qty:
            return False
        self._registry[from_pos]["qty"] -= qty
        if self._registry[from_pos]["qty"] == 0:
            del self._registry[from_pos]
        if to_pos not in self._registry:
            self._registry[to_pos] = {"qty": 0, "radius": new_radius}
        self._registry[to_pos]["qty"] += qty
        self._registry[to_pos]["radius"] = new_radius
        return True
为什么要有: GoldCoin 是可互换的——50 个金币在同一个位置不需要 50 个 entity。一张字典、qty 字段、一组坐标就够了。
谁调: NPC 执行 take_out / take / put_away / give 时引擎 dispatch 到这里。
什么时候调: 约束全部通过后。如果 qty 不足，move 返回 False——但正常情况下约束已护住。 
    def qty_at(self, pos) → int:
        return self._registry.get(pos, {}).get("qty", 0)
为什么要有: 约束校验用——"Geralt 手上有多少金币"。返回 0 意味着该位置没有金币。
谁调: qty_non_negative.validate()——PRE 阶段，在执行 move 之前。 
    def all_near(self, center_pos, view_radius) → list[dict]:
        result = []
        for pos, entry in self._registry.items():
            if entry["radius"] == 0:
                continue                       # r=0 pocket — 不可见
            d = abs(pos[0] - center_pos[0]) + abs(pos[1] - center_pos[1])
            if d <= max(entry["radius"], view_radius):
                result.append({"pos": pos, "qty": entry["qty"], "radius": entry["radius"], "distance": d})
        return result
为什么要有: Sensory 系统查询"observer 附近有什么"。跳过所有 r=0 条目。
谁调: SensorySystem.update()——每个 agent 每 tick 一次。遍历所有 SpatialObject 注册表。
关键修正: 需要加一个特殊情况——r=0 且 pos==observer.pos（自己的口袋）→ 包含。否则 NPC 看不见自己的金币。在 sensory.py 的调用侧处理，不改 SpatialObject。

2.3 Entity 实现 — IronSword

class EntitySpatial(SpatialObject):
    # 唯一物品——剑、门、陷阱。每个都是独立的 entity。

    def __init__(self, entity):
        self._entity = entity

    def move(self, from_pos, to_pos, qty, new_radius):
        self._entity.pos = to_pos               # 唯一物品——直接改坐标
        return True

    def qty_at(self, pos) → int:
        return 1 if self._entity.pos == list(pos) else 0   # 在此位置返回 1，否则 0

    def all_near(self, center_pos, view_radius) → list[dict]:
        d = abs(self._entity.pos[0] - center_pos[0]) + abs(self._entity.pos[1] - center_pos[1])
        if d <= max(self._entity.radius, view_radius):
            return [{"pos": self._entity.pos, "qty": 1, "radius": self._entity.radius}]
        return []
为什么要有: 确保剑和金币共享同一接口——约束系统不需要区分对象类型。qty_at 返回 0/1 而非查字典——但 validate 代码完全一致。
谁调: 同 ClassSingleton——约束和感官系统统一调用。
主要用例: 耐久度检查、是否存在的校验、唯一的可拾取物品。

3. SpatialProxy — 桥接 将 SpatialObject 注入现有 entity 管线

class SpatialProxy:
    # 30 行薄包装——将 GoldCoin 的一个位置堆叠变成 entity-like 对象
    # 解决: 13 处 world.entities 遍历——不改这 13 处代码——SpatialProxy 直接存入

    def __init__(self, spatial_obj, pos, qty, r, zone):
        self.id   = f"spatial:{spatial_obj.name}_{pos[0]}_{pos[1]}"
        self.name  = spatial_obj.name
        self.zone  = zone        # find_entity_by_name 需要 zone 过滤
        self._pos  = pos         # distance_to 需要坐标
        self._obj  = spatial_obj # 实际 SpatialObject——供 action dispatch
        self._qty  = qty
        self._r    = r
        self._stub = _SpatialInteractionLayer()  # interaction_radius=1
为什么要有 SpatialProxy: GoldCoin 是 class singleton——不在 world.entities 里。现有 13 处代码遍历 world.entities 查找可交互对象。SpatialProxy 把 GoldCoin 的一次位置堆叠包装成 entity-like 对象——直接存入 world.entities。这 13 处代码零改动。

不要新建文件——30 行在 interaction.py 中。 
    # ── 实体标识 (find_entity_by_name / logger) ──
    @property
    def pos(self): return self._pos
为什么要有: sensory system 调 distance_to——需要两个 entity 都有 pos。SpatialProxy 暴露 pos——与 Entity.pos 完全相同的接口。 
    # ── Layer 检查 (find_entity_by_name / can_interact 的过滤) ──
    def has(self, key):  return key == "interaction"
为什么要有: find_entity_by_name 过滤 `if not e.has("interaction"): continue`。can_interact 过滤 `if not target.has("interaction"): return False`。SpatialProxy 必须通过这两个过滤——所以暴露 `has("interaction") → True`。
这不是伪装——这是正确的: GoldCoin 的堆叠是可交互的——暴露 interaction layer 是准确的。
重要: 不暴露 `has("spatial") → True`——不需要。spatial target 和 item 走同一条路径。交互系统的 else 分支通过检查 `get("interaction")` 上是否有 spatial 标记来分派。 
    def get(self, key):
        if key == "interaction":
            return self._stub    # 暴露 interaction_radius=1
        return None
为什么要有: can_interact 调 `target.get("interaction").interaction_radius`。SpatialProxy 暴露一个 stub interaction layer——interaction_radius=1。
为什么半径是 1: 近距离——agent 必须紧邻才能交互。这和 NPC↔NPC 的 interaction_radius 一致。

    @property
    def layers(self):
        return {"visual": self._visual_layer, "interaction": self._stub}
为什么要有: sensory.py 遍历 `entity.layers.items()`——对每个有 `observe()` 的层调 `observe(d)`。这是金币作为感官物体被感知的方式。
为什么暴露视觉层: 金币通过视觉层暴露给 LLM。不暴露听觉层——金币不会说话。

4. Constraint System 约束系统

4.1 Constraint ABC

class Constraint(ABC):
    # 所有物理定律的基类。30 行。引擎只知此接口。
    # 新增约束 = 继承此基类 + @register 装饰器 + YAML 声明一次。

    timing: str = "pre"            # "pre" / "exec" / "post" — 约束自己声明

    def activation(self, entities, action_def) → bool:
        pass
为什么要有: 不是每个约束每次交互都触发。约束自己决定"这次需要我吗"。引擎循环所有约束，逐个调 activation()——True 的参与本轮。
什么情况会 True: qty_non_negative → "resource" in action_def。conservation → "transfer" in action_def。durability → target 是 entity 且有 durability 属性。
引擎不知道激活条件——每个约束自己决定。 
    def validate(self, entities, action_def, world) → (bool, str):
        pass
为什么要有: 校验物理可行性。返回 (通过, 失败原因)。引擎按 timing 分组——每个组内逐个 validate——任一失败→停止。
什么情况会失败: qty_non_negative——obj.qty_at(pos) < amount。
失败后发生了什么: 引擎返回 Result(failed=c, reason=reason)。LLM 下轮通过感官通道感知失败原因。 
    def apply(self, entities, action_def, world):
        pass
为什么要有: 执行物理操作。只在 validate 通过后调用。原子——一次完成。
什么约束用 apply: conservation——ledger.transfer()。consumption——qty-1 + deltas + 若归零则移除。qty_non_negative——pass（纯门控——move 由 SpatialObject 执行）。
为什么不是每个约束都需要 apply: 门控型约束（qty check）只校验不执行。操作型约束（consumption）校验通过后执行物理操作。

4.2 Registry + process()

class ConstraintRegistry:
    _constraints: dict[str, Constraint] = {}                    # {"qty_non_negative": instance}

    def register(self, name, constraint):                    # 一行装饰器
        self._constraints[name] = constraint

    def process(self, entities, action_def, world):            # 引擎一行调
        active = [c for c in self._constraints.values()
                  if c.activation(entities, action_def)]
        for group in ["pre", "exec", "post"]:
            for c in [c for c in active if c.timing == group]:
                ok, reason = c.validate(entities, action_def, world)
                if not ok:
                    return ProcessResult(failed=c.name, reason=reason)
                c.apply(entities, action_def, world)
        return ProcessResult(ok=True)
为什么要有 process: 引擎唯一调用的入口。不认识约束名——不认识 timing——不认识 gold。只循环 + 分组 + 调 validate + 调 apply。
谁调: interaction.py 在交互执行前调 constraints.process()。
为什么分组: pre 失败→不执行任何 apply。exec 失败→不执行 post。post 不做门控——只记日志。三个组在逻辑上有序——但引擎只循环。

4.3 qty_non_negative — 具体约束

@register("qty_non_negative")
class QtyNonNegativeConstraint(Constraint):
    timing = "pre"       # 在 action 执行前校验

    def activation(self, entities, action_def):
        return "resource" in action_def      # 涉及资源 → 需要数量校验
为什么检查 "resource" 字段: 不是每个交互都涉及资源。talk() 不用校验数量。take_out(gold,5) 定义了 resource 和 qty——需要校验。
什么交互有 "resource": take_out、take、give、eat、pick_up——任何移动或消耗物品的交互。
什么交互没有 "resource": talk、walk、follow、open。 
    def validate(self, entities, action_def, world):
        obj  = action_def["spatial_obj"]       # GoldCoin / IronSword / AppleCrate
        pos  = action_def["from_pos"]          # 从哪个位置移出
        need = action_def.get("qty", 1)         # 需要多少
        have = obj.qty_at(pos)                    # 该位置当前有多少
        ok = have >= need
        reason = f"{obj.name}: need {need}, have {have}" if not ok else ""
        return ok, reason
为什么调 qty_at(pos): 不查"谁的余额"——只查"这个位置有多少"。引擎不知道所有权。
什么情况会失败: Geralt 只有 3 金币在金库，想 take_out 5 金币 → have=3, need=5 → False → "Gold: need 5, have 3"。
失败后: 引擎停止。Geralt 下轮感官感知口袋金币没变——LLM 自己推理"钱不够"。 
    def apply(self, entities, action_def, world):
        pass      # 门控约束——不做物理操作
为什么不执行 move: 移动是 SpatialObject.move() 的事——不是约束的事。约束只做准入控制。引擎在 process() 返回 ok 后自己调 SpatialObject.move()。

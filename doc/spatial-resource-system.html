Items have only 3 atomic operations. Constraints bind to entities — any qty change triggers. LLM uses natural language — engine infers intent — calls the right atomic op.

1. Design Principles 设计原则

① Item 只有原子 CRUD

split(qty) / merge(other) / move_to(pos)。这就是一切。没有 take_out / put_away / give —— LLM 描述意图，引擎调原子的 split/merge/move_to。

② 约束绑在 entity 上

不绑在 action 上。gold entity 声明 constraints: [qty_non_negative]——任何代码路径修改 qty 都触发校验。捡钱、赚、偷——全走同一约束。

③ LLM 自然语言

LLM 不说 "take_out"。LLM 说 "这5个金币你收下" + item_ops: [{split:5, to:hand, r:1}]。引擎推断出要 split gold entity。

④ r=-1 仅自己可见

口袋 entity 的 radius=-1。sensory 一行过滤：r<0 and pos!=observer → skip。零特殊情况。

⑤ 全 Entity 统一

Gold 是 Entity。Sword 是 Entity。唯一的区别是 private_attrs.qty。qty=1 是唯一物——qty>1 是可互换物。

2. Entity with qty Entity + qty — 全物统一

2.1 YAML — Gold 和 Sword 的声明完全同结构

# 唯一物 — qty=1 隐式
- id: iron_sword
  zone: bar_zone  pos: [10, 15]
  interaction:
    private_attrs: {durability: 100, radius: 1}

# 可互换物 — qty=50, 约束绑在 entity 上
- id: gold_geralt_pocket
  zone: bar_zone  pos: [12, 7]
  interaction:
    constraints: ["qty_non_negative"]     ← 任何 qty 变更都触发
    private_attrs: {qty: 50, radius: -1}  ← r=-1: 仅 Geralt 可见
  visual:
    properties: {look: "golden coins"}
约束不绑在 action 上——绑在 entity 上。 Gold entity 的 qty 字段只要被修改——不管是 split 还是 merge 还是外部 Director.set——qty_non_negative 都触发。因为约束是 entity 的属性——不是某种特定交互的属性。

Constraints bind to entities, not actions. When gold entity's qty is modified — whether by split, merge, or external Director.set — qty_non_negative fires. Because the constraint belongs to the entity — not to a specific interaction type.

3. LLM Decision — Natural Language + item_ops LLM 决策：自然语言 + item_ops

LLM 不需要知道 split / merge 这些接口名。LLM 输出自然语言意图——引擎从感官上下文中推断具体操作。

# LLM 的 JSON 输出 — 自然语言为主，item_ops 是辅助字段
{
  "action": "拿出5枚金币放在手心",
  "dialogue": "这5个金币你收下",
  "target_name": "Rachel",
  
  "item_ops": [{                            # ← 可选: LLM 描述涉及物品的操作
    "entity": "gold",                        # 哪个 entity
    "qty": 5,                               # 涉及多少
    "to": "hand",                            # 移动到哪 (optional)
    "radius": 1                            # 新半径 (optional)
  }]
}
引擎做的事: 读取 item_ops——遍历每个 op——从 world.entities 找到对应 entity——检查 entity 上的 constraints——通过后调 entity.split(qty) 或 entity.move_to(pos)。引擎不知道"这是拿出金币"——只知道"这里有个 entity，它要拆出 5 个，移动到 hand 位置，半径设为 1"。

What the engine does: reads item_ops — for each op — finds the entity in world.entities — checks constraints on the entity — if pass, calls entity.split(qty) or entity.move_to(pos). Engine doesn't know "this is taking out gold" — it just knows "this entity needs to split 5, move to hand position, radius=1".

4. Constraint System 约束系统

约束绑在 entity 的 constraints 列表上——不是绑在 action 上。任何代码路径修改 entity 的 qty，都先检查 entity 上的约束。

4.1 Constraint ABC

class Constraint(ABC):
    # 30 行基类。新增约束 = 继承此类 + @register 装饰器。
    timing: str = "pre"

    def activation(self, entity, op) → bool:
        pass
为什么: 约束自己判断是否需要触发。不是每个 entity 都有 qty 约束。
qty_non_negative 激活: entity 的 constraints 表里有它 + op 涉及 qty 修改 → True。
引擎不知道激活条件——约束自己决定。 
    def validate(self, entity, op, world) → (bool, str):
        pass
为什么: 校验物理可行性。返回 (通过, 失败原因)。
不通过: 引擎不执行 entity 的 qty 修改。LLM 下轮从感官感知失败。 
    def apply(self, entity, op, world):
        pass
为什么: 只在 validate 通过后调用。原子——无状态残留。
门控约束: qty_non_negative — pass（不做操作——split 由 Entity 执行）。
操作约束: consumption — 消耗后 entity 归零→移除。

4.2 Engine Dispatch — 任何 qty 变更都经过这里

def modify_entity_qty(entity, op, world):
    # entity 的 qty 被修改的唯一入口。任何代码路径都走这里。
    # LLM 自然语言描述 → 引擎推断 → 调 split/merge → 调此函数 → 约束触发。

    constraints_list = entity.interaction.constraints     # e.g. ["qty_non_negative"]
    for name in constraints_list:
        c = REGISTRY[name]
        if c.activation(entity, op):
            ok, reason = c.validate(entity, op, world)
            if not ok: return Result(failed=name, reason=reason)
            c.apply(entity, op, world)
    return Result(ok=True)
为什么这是唯一入口: 无论 LLM 怎么描述意图——"拿出金币"、"给金币"、"偷金币"、"捡金币"——最终都是调 entity.split() / merge() / move_to()。而这三个方法内部都先调 modify_entity_qty——触发 entity 上的约束。
不需要新的接口: 捡钱？entity.split(amount_from_ground)。赚到钱？entity.split(amount_from_reward)。都是 split。不需要每个场景都加接口名。

6. Full Scenario — Gold Transfer 完整场景——金币转移

Tick N — Geralt: 拿出 5 金币 + 说话
│
├─ LLM: {action: "拿出5枚金币", item_ops: [{entity:"gold", qty:5, to:"hand", radius:1}]}
├─ 引擎: 找到 gold entity → entity.constraints = [qty_non_negative]
├─ modify_entity_qty(gold_entity, {qty:5, to:hand, r:1})
│ └─ qty_non_negative.validate → gold_entity.qty=50 ≥ 5 → ✓
│ └─ gold_entity.split(5) → 源 qty:50→45, 新 entity(qty=5, r=1) 在 hand 位置
├─ LLM: {dialogue: "这5个金币你收下"} → write auditory layer
│
├─ Rachel's sensory:
│ └─ Gold (0格, r=1) — at Geralt's hand position
│ └─ conversation: "[1s] Geralt: 这5个金币你收下"
│ └─ LLM: "他拿出金币 + 说'收下' → 我要拿吗？"
│
├─ Tick N+1 — Rachel: 拿走金币
│ └─ LLM: {item_ops: [{entity:"gold", qty:5, to:"hand", radius:1, from:Geralt_hand}]}
│ └─ modify_entity_qty(hand_gold, {qty:5, to:Rachel.hand, r:1})
│ └─ qty_non_negative.validate → hand_gold.qty=5 ≥ 5 → ✓
│ └─ hand_gold.move_to(Rachel.hand_pos) → done
│ └─ LLM: {item_ops: [{entity:"gold", to:"pocket", radius:-1}]} → merge hand→pocket
│
└─ Tick N+2 — 双方感知:
     Geralt: hand qty=0 → "她收了"。Rachel: pocket qty=8 → "+5"。
无 proposal。无 pending。无两阶段。无 action-specific 接口。 只有 LLM 的自然语言 + 引擎对 entity 原子操作的执行。约束绑在 entity 上——任何 qty 变更自动触发。

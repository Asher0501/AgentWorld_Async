1. Why This Exists 为什么需要这个系统

Before · 之前

金币是一个数字——geralt.gold = 50。取钱靠查账本、转账靠改余额。需要额外的 ledger 模块、resources 通道、balance 校验。

After · 之后

金币是空间里的物体——位置 (x,y)、数量 qty、可见半径 radius。拿出金币 = 移到自己手上。给人金币 = 对方从手上拿走。sensory 通道天然覆盖。

From "how much gold do I have" to "where is the gold" · 从"我有多少金币"到"金币在哪里"

2. The Core Idea 核心思想

关键洞察: 不需要账本、不需要余额字段、不需要独立的 resources 感官通道。现有的 sensory 通道天然覆盖——gold 就像任何其他 entity，通过半径可见。引擎不知道 gold 是什么——它只知道"这里有一个空间物体，半径 X，数量 Y"。

3. Three-Layer Architecture 三层架构

4. Constraint — A Self-Contained Physical Law 约束——自包含的物理定律

activation() — 我该不该触发？

约束自己判断: 这次交互跟我有关吗？
双方都声明了 conservation → 激活。
只有一方声明 → 不激活。

timing — 我在哪个阶段工作？

"pre" = 执行前校验。余额检查。
"exec" = 执行中操作。扣减数量。
"post" = 执行后记录。记日志。

validate() — 现在能行吗？

校验物理可行性。返回 True/False。
不通过: 返回具体原因。
引擎拿到结果 — 不执行 apply。

apply() — 执行

只有 validate 通过后才调用。
原子操作——一次完成，无状态残留。
引擎不关心 apply 里做了什么。

引擎的视角: 引擎有一组约束名。引擎把它们按 timing 分组。引擎循环调 validate → apply。引擎不知道 conservation 是什么、不知道 gold 是什么、不知道"qty_non_negative"是什么意思。引擎只知道调完返回成功或失败。

5. Example: Gold Transfer 范例：金币转移

核心观察: 没有 pending、没有两阶段、没有 ledger、没有 resources 通道。整个过程就是两次物理移动——Geralt 从口袋拿到手，Rachel 从 Geralt 手拿到自己手再放进口袋。每次移动都是独立的约束校验。Rachel 自己决定接不接受——引擎不替她做决定。

6. Constraint Dispatch 约束派发

引擎只做一件事：按 timing 分组，每组内逐个调 validate → apply。

新增约束: 三步——写一个 25 行的类 + @register + YAML 里声明。引擎零改动。约束自己决定 timing、自己决定什么时候激活、自己决定怎么校验。引擎只负责分组和循环。

7. Why This Architecture 为什么这个架构

Design Goal · 设计目标How It's Achieved · 如何实现
金币和石头统一金币是空间里的物体——和 NPC 一样通过 sensory 通道感知。不需要独立的 resources 通道。
物理守恒自动保证物体不能同时在两个地方。移动即转移。不存在凭空创造或凭空消失。
约束独立可扩展每个约束是一个类。新增约束 = 加一个文件 + 一行装饰器。引擎不感知。
引擎零领域知识引擎不知道 gold、conservation、consent 是什么。只知道调 process()。
感知闭环自然闭合约束失败 → 世界不变 → LLM 下轮感知 → 重新决策。不需要重试机制。
交互模式不耦合约束Action 接口负责"要不要等对方确认"。约束负责"物理上能不能做"。两层独立。
可互换 vs 唯一物品并存可互换资源走类单例注册表。唯一物品走 entity。同一引擎、同一感官通道。
YAML 是扩展面新资源类型 → 加一个类单例 + YAML 声明。新约束 → 加一个类 + YAML 声明。零引擎改动。

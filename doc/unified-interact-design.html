1. Two Interaction Paradigms 两种交互范式

Proposal-Consent 要约-同意

NPC ↔ NPC — both sides have LLM cognition.
Phase 1: proposer sends propose: send gold=5 + dialogue.
Phase 2: target perceives via conversation_text, decides accept/reject/counter.
Phase 3: only on accept → engine validates constraints + executes.
Dispatch: target.has("agent") = the only branch point.

Direct Execution 直接执行

NPC → Item — target has no LLM. No proposal phase.
NPC decides eat apple → engine validates constraints immediately → executes.
Item's feedback defined by YAML rules.
Dispatch: same interact() — no separate code path.

3. Universal Constraint Paradigm 通用约束范式

Constraints are physical laws — not value judgments. Every constraint — conservation, consumption, capacity, reputation, durability, access — follows the same interface, the same registration pattern, and the same engine processing loop. The engine never distinguishes one constraint from another.

Abstract Interface 抽象接口

All constraints implement 3 methods + 1 property. Zero domain knowledge. The engine sees: validate(), apply(), describe_failure(), phase. Nothing else.

Match + Activate 匹配+激活

match(agent_constraints, target_constraints) → set[name]. Only constraints registered by both parties activate. Single-party registration is silently ignored.

Phase Control 相位控制

phase = "propose" | "execute" | "both". Proposal-phase constraints (capacity, reputation) check during proposal. Execute-phase constraints (conservation, consumption) check during execution.

@register Decorator 装饰器注册

One decorator: @register("name"). Auto-adds to _REGISTRY. Zero engine changes needed to add a new constraint type.

3.1 The Abstract Interface 抽象接口定义

class Constraint(ABC):
    # 物理定律基类。引擎只知此接口。Base class. Engine knows ONLY this interface.

    phase: str = "execute"   # "propose" | "execute" | "both" — 何时激活

    def validate(self, agent, target, action_def, ledger, world) → bool:
        # 校验物理可行性。返回 True/False。零认知判断。
        ...

    def apply(self, agent, target, action_def, ledger, world):
        # 执行物理操作。校验通过后调用。引擎只知 side-effect。
        ...

    def describe_failure(self, agent, target, action_def) → str:
        # 事实描述 — 为什么失败。不判断 — 只报事实。
        # Never: "your inventory is too full". Always: "capacity: 10/10".
        ...

3.3 The Engine Processing Loop 引擎统一处理循环

# interaction.py — 引擎只循环 active 约束集，不区分约束类型
# The engine only loops over the active constraint set. Never branches on constraint type.

def interact(agent, target, decision, world):
    action_type = decision.get("interact")

    agent_cons = agent.interact[action_type].get("constraints", [])
    tgt_cons   = target.interact[action_type].get("constraints", [])

    active = REGISTRY.match(agent_cons, tgt_cons)
    # e.g. {"conservation", "capacity"} — 全是名字, 引擎不知道它们做什么

    # PROPOSE phase: only NPC↔NPC (target has LLM)
    if target.has("agent"):
        for name in active:
            c = REGISTRY[name]
            if c.phase in ("propose", "both"):
                if not c.validate(agent, target, defs[action_type], ledger, world):
                    return ActionResult(error=c.describe_failure(...))
        store_pending_proposal()
        return

    # EXECUTE phase: NPC↔Item or NPC↔NPC on accept
    for name in active:
        c = REGISTRY[name]
        if c.phase in ("execute", "both"):
            if not c.validate(agent, target, defs[action_type], ledger, world):
                return ActionResult(error=c.describe_failure(...))
            c.apply(agent, target, defs[action_type], ledger, world)
    log.result()
引擎零认知 / Engine Zero Cognition: The engine never checks "is this about gold or mana or reputation?" It loops over active, calls validate(), calls apply(). Each constraint class encapsulates its own physics. The engine is a constraint-agnostic executor.

3.4 Registration — One Decorator 注册——一行装饰器

# constraints/__init__.py
_REGISTRY = {}

def register(name: str):
    def decorator(cls):
        _REGISTRY[name] = cls()
        return cls
    return decorator

def match(agent_constraints: list, target_constraints: list) → set[str]:
    return set(agent_constraints) & set(target_constraints)
Extend / 扩展: Add 1 file in constraints/: 30 lines implementing Constraint. One @register("new_name") decorator. Then YAML can reference it via constraints: ["new_name"]. Zero engine code changes. Zero loop.py changes.

4. Worked Example: Conservation Constraint 具体范例：守恒约束

Conservation is one constraint among many. It follows the exact same interface, registration pattern, and engine processing loop as every other constraint. This section walks through its complete lifecycle.

4.1 Implementation — 30 Lines 实现

# constraints/conservation.py
from . import Constraint, register

@register("conservation")
class ConservationConstraint(Constraint):
    phase = "execute"   # 只在执行时校验

    def validate(self, agent, target, action_def, ledger, world=None) → bool:
        resource = action_def["resource"]
        amount   = action_def.get("amount", action_def.get("cost", 1))
        return ledger.balance(agent.id, resource) >= amount

    def apply(self, agent, target, action_def, ledger, world=None):
        resource = action_def["resource"]
        amount   = action_def.get("amount", action_def.get("cost", 1))
        ledger.transfer(agent.id, target.id, resource, amount)

    def describe_failure(self, agent, target, action_def) → str:
        resource = action_def["resource"]
        bal = ledger.balance(agent.id, resource)
        need = action_def.get("amount", action_def.get("cost", 1))
        return f"{resource}: balance {bal} insufficient for {need}"

7. Resource Ledger 资源账本

Flat entity-level balance sheet. Zero domain knowledge. Every constraint type that involves resource tracking uses this same ledger.

class ResourceLedger:
    # {entity_id: {resource_name: quantity}} — 不知道 gold/mana/apple 是什么
    _holdings: dict[str, dict[str, int]]

    def balance  (entity_id, resource) → int
    def all_of   (entity_id) → dict[str, int]         # → resources channel
    def transfer (src, tgt, resource, amount) → bool  # atomic, no partial
    def deposit  (entity, resource, amount)              # world → entity
    def withdraw (entity, resource, amount) → bool    # entity → void
Ledger as sensory channel / 账本作为感官通道: ResourceSource.collect() calls ledger.all_of(agent.id) → ctx["resources"] → LLM sees: gold: 45\npotions: 2. The LLM perceives resource changes just as it perceives sensory changes. The ledger is a state store — the channel is the perception interface.

9. Design Philosophy 设计哲学对齐

Engine as Constraint-Agnostic Executor

The engine loops over constraint names. Calls validate(). Calls apply(). Never distinguishes conservation from capacity from reputation. The constraint class encapsulates its own physics.

Sensory-Driven Consent

No "proposal channel". The target LLM perceives through conversation_text. The engine never tells LLM "someone wants to give you gold." LLM infers it from dialogue — just as humans do.

Physics ≠ Economics

Constraints validate physical feasibility — balance, durability, capacity. The engine never judges whether a trade is fair, a gift is appropriate, or a duel is wise. LLM decides. Engine checks laws.

@register is the Extension Boundary

New constraint = 1 new file + @register. Zero engine changes. The constraint paradigm is the grammar — conservation is one sentence in that grammar.

Closed Loop Across All Interactions

6 channels → LLM decide → interact dispatch → constraint loop → ledger update → log → next tick perception. Cycle invariant across NPC↔NPC, NPC↔Item, Item→NPC.

Silence, Rejection, Emptiness

If Rachel doesn't accept the gold, the engine doesn't force it. If Geralt proposes a trade no one takes, the pending proposal sits — LLM eventually decides to withdraw. No engine intervention.

1. Two Interaction Paradigms 两种交互范式

Proposal-Consent 要约-同意

NPC ↔ NPC — both sides have LLM cognition.
Phase 1: proposer sends propose: send gold=5 + dialogue.
Phase 2: target perceives via conversation_text, decides accept/reject.
Only on accept: engine validates constraints + executes.
Applicable to: send, trade, give_item, challenge, recruit, ...

Direct Execution 直接执行

NPC → Item — target has no LLM. No proposal phase.
NPC decides eat apple → engine validates constraint immediately → executes.
Item's response defined by YAML rules.
Applicable to: eat, pick_up, open, use, absorb, ...

判断依据 / Dispatch logic: if target.has("agent") → Proposal-Consent (目标有 LLM 认知, 需等待对方决定). else → Direct Execution (目标无 LLM, YAML rules 提供反馈). 引擎只问这一句——不做其他判断.

3. Proposal-Consent Protocol 要约-同意协议 (NPC↔NPC)

Three-phase, sensory-driven. No proposal channel — the target perceives via conversation_text. Engine validates only on accept.

引擎何时校验 / When does the engine validate:
Phase 1 (propose): Engine checks can_propose — sender balance satisfies constraint (prevent "bouncing checks"). Stores proposal as _pending_proposal. No transfer happens.
Phase 2 (target): Engine does NOTHING — Rachel's LLM perceives via conversation_text and decides freely. Zero engine intervention.
Phase 3 (accept only): Engine validates constraint with current sender balance, executes transfer, clears proposal. On reject: only clears the proposal.

3.1 Reject + Counter 拒绝 + 还价

# Rachel rejects / 拒绝
LLM decides: {action: "摇头", dialogue: "不了，我不需要施舍。",
              response: "reject", to: "Geralt", resource: "gold"}

FLUSH: find pending(geralt, gold) → delete. No transfer. Logged.

# Rachel counters / 还价
LLM decides: {action: "挑眉", dialogue: "10金币我帮你打听消息。",
              response: "counter", to: "Geralt", want: "gold", amount: 10,
              offer: "village info"}

FLUSH: delete old pending. Write new propose: Rachel→Geralt trade.
Geralt下轮感知 → 自己决定接受/拒绝。

4. Direct Execution 直接执行 (NPC→Item)

Target has no LLM. No proposal phase. NPC decides → constraint validates → executes immediately.

6. Constraint Registry + Ledger 约束注册中心 + 资源账本

ConstraintRegistry

match(agent_act, target_act) → set[name] — only constraints registered by both activate.
apply(name, agent, target, action, ledger) — dispatch to constraint class.

ConservationConstraint

validate: src.balance(resource) ≥ amount
apply: ledger.transfer(src, tgt, resource, amount)

ConsumptionConstraint

validate: target resource quantity > 0
apply: resource-1, apply deltas, if 0→remove entity

ResourceLedger

balance(id, res) → int | transfer(src,tgt,res,n)→bool
Zero domain knowledge. Flat entity-level balance sheet.
transfer(A,B,x,n) guarantees atomicity — no partial execution.

引擎何时校验 / When does the engine validate:
NPC→Item (Direct): validate + apply immediately — no proposal phase.
NPC→NPC (Proposal-Consent): Phase 1: can_propose check (balance satisfies). Phase 3: validate + apply only on accept. On reject: only clear pending proposal. On counter: delete old pending, write new.

8. Design Philosophy Alignment 设计哲学对齐

Sensory-driven protocol

No "proposal channel". Rachel's LLM perceives via conversation_text + action_feedback. Engine never tells LLM "someone wants to give you gold." LLM figures it out.

Engine validates physics, not economics

Constraint checks only physical feasibility (balance ≥ amount). Engine never judges whether a trade is fair, reasonable, or wise.

Two paradigms, one dispatch

target.has("agent") is the only branch point. Proposal-Consent vs Direct Execution determined by whether the target has cognition — not by action type name.

YAML is the extension surface

New action type → add YAML key. New constraint → add 1 class. New resource → add resources block. Zero engine dispatch changes.

Closed loop preserved

6 channels → LLM decide → interact dispatch → proposal/execute → ledger update → log → next tick perception. Cycle unchanged across all interaction types.

Silence and rejection are valid

If Rachel doesn't accept the gold, the engine doesn't force it. If Geralt proposes a trade no one accepts, the proposal sits pending — and the LLM eventually decides to withdraw it. No engine intervention.

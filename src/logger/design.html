1. 设计原则

零认知判断

引擎报告事实，LLM 提供认知，Logger 只记录。不计算"重复率够不够"、"情绪好不好"、"性能是否异常"——那都是 eval/ 的活。

被动观察者

Logger 不改变任何数据流。所有 hook 默认 no-op。引擎不知道 logger 在不在——也不应该知道。

一处定义，全局使用

6 个公开 hook 替代 3 个旧模块（agent_logging、error_collector、verification stdout）。统一入口 log，所有观测一个路径。

类宏开关

enable() — 全开。disable() — 全关。AW_LOG=path — 环境变量激活。开关外侧代码零感知。

和设计哲学的关系：引擎提供事实 → Logger 记录事实 → Eval 分析事实。Logger 不越过"判断"线。Error 就是 error、Latency 就是 latency——不评价 "好快" 或 "出问题了"。

2. 模块架构

核心原理：Hook 定义和实现全在 Logger 侧。引擎只管在正确的时间点喊一声 log.gate(...)。喊不喊、喊什么——这是引擎的职责。喊了之后谁听、怎么记录——这是 Logger 的职责。中间只隔了一个函数指针。

3. 6 个 Hook 详解

3.1 log.gate(agent, *, triggered, reason, zone, nearby, drives)

观测什么

Agent 内部世界模型 P 和感官 Q 是否相等。这就是著名的 "世界不变，Agent 不动" 这句话的物理时刻。

触发时机

Phase 2 (GATE) 末尾。每 tick 必呼叫一次。无论触发与否都会调用——这样才知道 agent 的"静默率"。

机制：引擎先通过 total_delta() 计算四通道差分（auditory、visual、spatial、state）。差异信号聚合成 delta_text 字符串。若为空 → P==Q，agent 本 tick 不思考。若非空 → 世界变了，触发 LLM 决策。

原理类比：像门口的运动感应灯。Logger 记录的不只是"灯亮了"——还记录"没亮"。灯没亮多少次，是能耗审计的关键指标。

例子：

# Ross 本人没变，P==Q，本 tick 跳过 LLM
log.gate("Ross", triggered=False, reason="",
         zone="central_perk", nearby=4,
         drives={"hunger": 40, "social": 70, "fun": 55})

# 三秒后，Rachel 走进感知范围，social drive 越过阈值
log.gate("Ross", triggered=True,
         reason="auditory: Rachel entered\nstate: social 70→75 (cross)",
         zone="central_perk", nearby=5,
         drives={"hunger": 41, "social": 75, "fun": 55})

3.2 log.decide(agent, *, action, intent, target, tokens, latency, retries)

观测什么

LLM 决定要做什么、花多少 token、耗时多少毫秒、重试了几次。这是整个系统的成本和性能核心指标。

触发时机

Phase 3 (DECIDE) 末尾，LLM 返回 JSON 决策后。

机制：引擎调用 brain.decide() → LLM 返回 JSON → 引擎提取 action/intent/target → 调用 log.decide()。token 数和延迟从 LLM response 对象拿（OpenAI API 响应体自带 usage.prompt_tokens 和 usage.completion_tokens）。

原理类比：像汽车的油耗记录仪。每次 LLM 调用是一次"加油→燃烧→输出"循环。记录 prompt (油量注入)、completion (燃烧产出)、latency (燃烧时间)——这些数据是优化模型选择、调 prompt 长度的实证基础。

例子：

# Ross 决定去跟 Rachel 搭话
log.decide("Ross",
    action="走向Rachel，站在她面前，紧张地搓手",
    intent="和Rachel搭话，尝试重建关系",
    target="Rachel",
    tokens=1520,        # prompt 1200 + completion 320
    latency=2340,       # 2.34 秒
    retries=0)

3.3 log.result(agent, *, action, target, narrative, deltas, sim, thread_done, duration, file_output)

观测什么

执行结果——对话内容、属性变化、主线是否完成、action 持续了多久、有没有产生输出文件（NPC 写代码）。

触发时机

Phase 0.5 (FLUSH) 末尾，action 执行完毕、deltas 已写入 layer、narrative 已生成。

机制：引擎在 FLUSH 阶段调用 interaction.interact() ——这是两个 NPC 之间的实际交互：对话生成（第二次 LLM 调用）、deltas 应用、main_thread 更新。全部执行完毕后，结果写入 trace。Logger 此时记录完整的因果链：谁对谁做了什么 → 说了什么 → 产生了什么变化。

原理类比：像 Git commit。gate 是 git status (看看变了没)，decide 是 git add (准备做什么)，result 是 git commit (做完了，写上 commit message)。三条记录构成一个完整的"世界变更事务"。

例子：

# Ross 对 Rachel 说完话后的完整结果
log.result("Ross",
    action="走向Rachel，站在她面前，紧张地搓手",
    target="Rachel",
    narrative="Ross对Rachel说了嘿，Rachel，呃……你最近怎么样？",
    deltas={"social": -10, "mood": 5},
    sim=5.63,           # 仿真时钟 5.63 秒
    thread_done=False,
    duration=3.0,       # action 表演了 3 秒
    file_output=None)     # 本次没写文件

3.4 log.error(agent, *, module, exception)

观测什么

异常捕获——什么模块抛了什么异常、traceback 是什么。

触发时机

任何 except 块的末尾。

机制：继承原 error_collector 的去重逻辑——相同 (module, message[:120]) 不追加新记录，只递增 count + 更新 last_at。raw traceback 完整保存供事后排障。

原理类比：像飞机的黑匣子——不是每个颠簸都开新记录，同类型的颠簸合并计数。只有新类型的故障才开新记录。黑匣子容量有限，去重是必要的压缩。

例子：

# 第 1 次 rate limit
log.error(agent="Rachel", module="loop.Rachel", exception=e)
# → errors 表: count=1, first_at=12.3, last_at=12.3

# 第 2 次 rate limit (同 module + message)
log.error(agent="Rachel", module="loop.Rachel", exception=e)
# → errors 表: count=2, first_at=12.3, last_at=18.7  ← 合并, 不新增行

3.5 log.warning(agent, *, module, message)

观测什么

非致命警告——属性越界、队列满、可能的数据不一致。

触发时机

verification.py 的 check_bounds 检测到越界时、event_bus 队列满时。

机制：原本是 print() 刷 stdout——不可查询、不可过滤、淹没在终端输出里。改为结构化入库后可通过 SQL 查询特定 agent、特定属性的越界频率。

例子：

log.warning(agent="Gunther", module="verification",
           message="[attribute_bounds] thirst would go below min: 1.7 + -15 = -13.3")

3.6 log.llm(provider, latency_ms, tokens, error)

观测什么

每次 LLM API 调用的原始延迟——不聚合、不统计。保留时序信息供延迟分布分析。

触发时机

llm/client.py 每次 API 调用完成（成功或失败）。

机制：与 telemetry collector 互补——telemetry 保留实时 中位数 给 DecisionClock 校准时钟。Logger 保留 每一条原始记录 给事后分析。这是"实时 vs 事后"的分工，不是"谁替代谁"。

原理类比：telemetry 是仪表盘上的瞬时油耗，logger 是加油站的每次加油记录单。仪表盘帮司机即时调整油门，记录单帮车主算月均油耗。

例子：

log.llm(provider="deepseek", latency_ms=2340, tokens=1520, error=False)

4. Hook 机制原理

4.1 为什么是类宏, 不是真正的宏?

Python 没有 C 预处理器。但可以用 可替换函数引用 做到同等效果：

class Log: # 6 个公开方法, 每个都是一对函数指针 def enable(self, storage): s = Session(storage) # 打开 SQLite self._gate = s.write # 把 6 个实现全换成真实写入 self._decide = s.write ·· def disable(self): self._gate = self._decide = ... = _noop # 全换回空函数 def gate(self, agent, **data): self._gate(agent=agent, phase="gate", **data) # 转发 def _noop(**kwargs): pass # 空实现 — 50 ns log = Log() # 全局单例 — 默认全部转发到 _noop
开关原理（分三步）：
Step 1 — 启动时: log.enable("logs/s001.sqlite3") → 打开 SQLite，把 6 个 self._hook 全换成 session.write。
Step 2 — 运行时: 引擎调用 log.gate("Ross", ...) → 转发到 self._gate → 进入 session.write → 追加到内存 ring buffer → 每 100 条异步刷 SQLite。
Step 3 — 运行时（关）: 不调 enable，所有 self._hook = _noop。引擎照样喊，但没人听。开销 = 一次 Python 函数调用，~50ns。

4.2 为什么是 6 个方法, 不是 1 个?

方案写法问题
单方法log("gate", agent, data)phase 是字符串 — 拼写错误运行时才发现; IDE 无补全
6 方法 ✅log.gate(agent, **data)IDE 自动补全; 参数名即文档; 写错参数类型 mypy 会报
context managerwith log.phase("gate"):只能捕获进入/退出时间。但 gate 数据在 with 块内部产生——拿不到 delta_text

4.3 为什么 3 个 hook 而不是 1 个 trace?

gate、decide、result 在代码里天然不连续：

log.gate() → 2〜5s → LLM 调用 → log.decide() → duraion 秒 → action 等待 → log.result()

中间夹了两个异步间隙——LLM 调用和 action 延迟。如果做成单个 trace 钩子，这三段数据必须缓存到函数局部变量，跨 await 边界保持。这破坏了"logger 不干预 engine 状态"的原则。

8. SQLite 表结构

ticks — 每决策周期一行

CREATE TABLE ticks (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    session    TEXT    NOT NULL,          # "session_001"
    agent      TEXT    NOT NULL,          # "Ross"
    tick_n     INTEGER NOT NULL,          # agent 的第 N 个决策周期
    wall_ts    REAL    NOT NULL,          # Unix timestamp
    sim_time   REAL,                       # 仿真时钟 (秒)

    -- Phase: GATE
    g_triggered INTEGER DEFAULT 0,       # 0=skip, 1=fired
    g_reason    TEXT,                       # "auditory:changed; state:cross"
    g_zone      TEXT,                       # "central_perk"
    g_nearby    INTEGER,                    # 周围实体数
    g_drives    TEXT,                       # JSON {"hunger":40,"thirst":...}

    -- Phase: DECIDE
    d_action    TEXT,                       # "走向Ross，拍拍他的肩膀"
    d_intent    TEXT,                       # "跟Ross打招呼"
    d_target    TEXT,                       # "Ross"
    d_tokens    INTEGER,                    # prompt + completion
    d_latency   REAL,                       # LLM 延迟 (ms)
    d_retries   INTEGER DEFAULT 0,

    -- Phase: RESULT
    r_narrative  TEXT,                      # "Ross对Rachel说了嘿..."
    r_deltas     TEXT,                      # JSON {"social":5,"fun":5}
    r_thread_done INTEGER DEFAULT 0,
    r_duration   REAL,                      # action 表演时长 (秒)
    r_file       TEXT                       # NULL 或 "coder_01_paging_sim.py"
);

errors — 去重异常记录

CREATE TABLE errors (
    id        INTEGER PRIMARY KEY,
    session   TEXT NOT NULL,
    agent     TEXT,
    module    TEXT NOT NULL,           # "loop.Ross"
    message   TEXT NOT NULL,           # "RateLimitError: too many requests"
    count     INTEGER DEFAULT 1,          # 重复次数
    first_at  REAL,                       # 首次发生时间
    last_at   REAL,                       # 最近一次时间
    traceback TEXT                        # 完整 traceback
);

llm_calls — 每次 API 调用原始记录

CREATE TABLE llm_calls (
    id         INTEGER PRIMARY KEY,
    session    TEXT NOT NULL,
    provider   TEXT,                      # "deepseek"
    latency_ms REAL NOT NULL,
    tokens     INTEGER,
    error      INTEGER DEFAULT 0,         # 0=ok, 1=失败
    wall_ts    REAL NOT NULL
);

9. 使用示例

9.1 类宏开关

from logger import log, enable, disable

# 方式 1: 环境变量 (零代码改启动脚本)
#   AW_LOG=logs/s001.sqlite3 python main.py ...

# 方式 2: 显式开关
enable("logs/session_001.sqlite3")   # 开 — 从此所有 hook 生效
# ... 运行仿真 ...
disable()                                 # 关 — 回到 no-op

9.2 查询分析 (eval 用)

-- 哪个 agent 的 gate 触发率最高？
SELECT agent,
       COUNT(*) AS total,
       SUM(g_triggered) AS fired,
       ROUND(100.0*SUM(g_triggered)/COUNT(*), 1) AS pct
FROM ticks GROUP BY agent ORDER BY pct DESC;

-- LLM 延迟 P50/P95/P99
SELECT
  ROUND(AVG(d_latency), 0) AS avg_ms,
  ROUND(MEDIAN(d_latency), 0) AS p50_ms,
  ROUND(PERCENTILE(d_latency, 0.95), 0) AS p95_ms
FROM ticks WHERE d_latency IS NOT NULL;

-- 每个 agent 的错误分布
SELECT agent, module, message, MAX(count) AS n
FROM errors GROUP BY agent, module
ORDER BY n DESC;

10. 性能分析

场景模式单次 hook 开销3min 总开销 (164 ticks × 3 hooks)
默认 (无 AW_LOG 环境变量)no-op~50 ns~24 µs (基本为零)
开启 (ring buffer 追加)内存 dict append~5 µs~2.5 ms
开启 + 刷盘 (100 条批写)SQLite executemany摊平后 ~50 µs/条~25 ms (异步, 不阻塞)
结论：开启时，3 分钟仿真 logger 总开销 < 30ms = 0.017% 的墙钟时间。关闭时 < 30µs = 基本为零。不影响世界运行。

11. 总结

6 个 Hook

gate · decide · result
error · warning · llm

覆盖引擎全生命周期观测

类宏开关

enable() / disable()
AW_LOG=path

定义与实现全在 logger 侧

9 行改动

3 文件 · 不改核心逻辑

loop.py +5, llm/client.py +3, interaction.py +1

统一 3 模块

删 agent_logging.py
删 error_collector.py
保留 telemetry (互补)

3 张表

ticks · errors · llm_calls

SQLite · JSONL 兜底 · 异步刷盘

零运行时开销

默认 no-op ~50ns/次

开启 < 0.02% 墙钟时间

设计哲学对齐：
1. 引擎报告事实 → Logger 记录事实 → eval 分析事实。Logger 不越过判断线。
2. 被动观察者 → Hook 是引擎主动调用，但 logger 不反写任何引擎状态。引擎不知道 logger 在不在。
3. 一处定义 → log.gate/decide/result/error/warning/llm 是唯一入口。所有观测数据从这 6 个门出去。
4. 即插即用 → 9 行改动，不影响任何现有 behavior。默认关闭，打开即生效。
